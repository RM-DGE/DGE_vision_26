# EKF 仿真测试指南

适用：hhh 当前 RobotModel4_v0.60。源码核对日期：2026-11-11。

目的：用户在 Linux 启动仿真器，AI 读取工程实际产生的数据，判断初始化、像素更新、关联和恢复是否正常，再用同一段输入验证参数修改。先完成单目标四装甲板测试，再增加复杂场景。

## 1、运行前先确认入口

**当前本机源码的仿真入口尚未接通，不能仅凭 `configs/daedalus.yaml` 的注释认为可以直接运行。** Linux 工程可能不同，执行测试的 AI 必须重新检查以下三项：

1. `src/standard.cpp` 的有效 `main()` 直接创建 `io::CBoard`，仍会打开实机串口；文件前面的旧实现已经注释。配置 `cboard_name: daedalus` 本身不会让这个入口切换到 `DaedalusCBoard`。
2. 有效代码仍查询 `cboard.imu_at(t - 1ms)`。Daedalus 相机适配器按图像帧号匹配姿态，并以图像读取时间写入姿态缓存；仿真配置的 `imu_delay_ms: 0` 没有在此入口生效。需要验证使用的是对应帧的姿态，不能直接套用实机的经验补偿。
3. 有效代码没有读取 `camera.ground_truth()`、调用 `publish_ground_truth()`，也没有把真值传给 `publish_debug()`。当前 Foxglove 的真值误差和 `/sim/ground_truth` 因而没有有效来源。

应先确认 Linux 上的启动程序已使用匹配的图像、姿态和指令后端，再进行第 2 节。若仍是上述代码，先报告“仿真接入未完成”，不要将串口、无图像、姿态错配等问题归因于 EKF。本指南只提供测试方法，不代表这些接入问题已经修复。

仓库中存在的是 Daedalus 共享内存适配器；若用户启动的是另一套 `rm_aim_sim`，必须核对协议和入口，不能假定兼容。仿真器启动命令以该 Linux 环境中的实际程序为准。

## 2、Linux 采集流程

以下命令均在 Linux 的 hhh 工程根目录执行。**在线运行命令仅在第 1 节接入检查通过后使用。**

### 2.1 正常编译

```bash
cmake -S . -B build -DEKF_ONLY=OFF -DTIME_SYNC_ONLY=OFF -DBUILD_TESTING=OFF
cmake --build build --target standard -j2
```

依赖应沿用该 Linux 工程原有安装。若编译缺少相机 SDK 或 OpenVINO，先处理构建环境；这不属于算法效果测试。保存本次源码版本及未提交修改、运行配置和检测模型版本，避免使用不同程序却认为是在比较参数。

### 2.2 运行并保留数据

先由用户启动仿真器。下面以“静止目标”场景为例，每换一个场景重新运行程序，并把目录名中的 `static` 改为对应场景名。

```bash
export HHH_EKF_RECORD_DIR="$PWD/logs/ekf_eval/static_$(date +%Y%m%d_%H%M%S)"
mkdir -p "$HHH_EKF_RECORD_DIR"
set -o pipefail
./build/standard configs/daedalus.yaml 2>&1 | tee "$HHH_EKF_RECORD_DIR/terminal.log"
```

需要本地窗口时，在配置路径后加 `-d`。正常结束用 `Ctrl+C`，留意退出错误；不要依靠强制杀进程保存最后几帧。

Tracker 创建时会自动记录，无需再开启 YAML 开关，也不要求 Foxglove 已连接。终端会打印：

```text
[EKF] recording .../某个数字目录
```

**这个数字目录才是后面回放使用的 `RUN_DIRECTORY`。** 目录结构如下：

```text
logs/ekf_eval/场景_日期时间/
├── terminal.log
└── 数字目录/
    ├── manifest.json
    ├── config.yaml
    ├── observations.jsonl
    └── trace.jsonl
```

每段测试结束，记录场景、目标运动设置、遮挡的大致时段，以及异常在画面中发生的时间。建议每段 20～30 秒，初始化和遮挡恢复另做重复试验。

### 2.3 Foxglove 现场观察

导入 [ekf_debug_layout.json](../foxglove_layouts/ekf_debug_layout.json)，连接算法所在电脑的 `ws://<IP>:8765`；同一台电脑可用 `ws://127.0.0.1:8765`。保留原 3D、窗口和状态表，使用现有五个曲线面板：

| 面板 | 实际字段 | 看什么 |
|---|---|---|
| 水平像素残差 | `/dge/debug.pixel_residuals[i].upper_u`、`lower_u` | 水平方向持续偏差、换板时的异常尖峰 |
| 垂直像素残差 | 同一编号的 `upper_v`、`lower_v` | 高度、姿态、角点误差；与水平残差对照 |
| 更新前 NIS | `pixel_nis_max`、`nis_threshold` | 不匹配何时发生；当前参考线不是实际拒绝阈值 |
| 半径与高差 | `state[8]`、`state[9]`、`state[10]` | 几何收敛、触边、错误换板后漂移 |
| 位置不确定度 | `sigma_x`、`sigma_y`、`sigma_z` | 更新后是否合理收缩，遮挡时是否增长 |

编号 `i=0…7` 是模型端点对，`2k`、`2k+1` 对应第 `k` 块装甲板。布局默认只显示编号 0，可勾选当前有效编号；重建后编号不保证仍对应同一实体。代码中的 `lightbar` 在这里表示参与像素观测的上下端点对。

状态表 `/dge/debug.ekf_status` 用于查看位姿解算状态、接受/拒绝次数、关联和恢复提示；转速继续在 3D 查看，无需另加曲线。布局文件只是显示配置，不保存运行数据。AI 定量分析以 JSONL 为主；截图可用于核对画面，不能替代逐帧记录。

## 3、AI 实际可以读取哪些数据

### 3.1 自动记录文件

| 文件 | 内容 | 使用边界 |
|---|---|---|
| `manifest.json` | 数据格式、算法标识、源码摘要、配置摘要、OpenCV/编译器信息 | 源码摘要覆盖 `tasks/auto_aim` 与 `tools/ekf_*`，不覆盖整个程序；仍需核对入口、相机适配器等修改 |
| `config.yaml` | 本次启动配置副本 | 分析这份配置，不能拿后来修改的 `configs/daedalus.yaml` 解释旧记录；未写的参数还需查当时源码默认值 |
| `observations.jsonl` | `frame_id`、`timestamp_ns`、相机模型/姿态、原始识别结果及角点 | 输入是在 Tracker 筛选和排序之前保存的；不是相机视频，也不是原始 IMU 流 |
| `trace.jsonl` | 同一帧的 Tracker 状态、目标状态、协方差、更新诊断、恢复信息和估计耗时 | `target: null` 表示此记录没有输出目标；内部失败现场不一定完整保留 |

两份 JSONL 以 **`frame_id` 和 `timestamp_ns`** 对齐。`timestamp_ns` 是图像所用的主机 steady clock 时间，分析横轴使用 `(timestamp_ns - 首帧时间)/1e9`，不要当作日历时间。

记录每 30 帧刷新一次；在线读取时只分析完整 JSON 行，停止后再核对尾部。没有独立的 `complete` 标志；若出现 `[EKF] recording unavailable/stopped`，本段数据可能缺失，必须注明。

### 3.2 `trace.jsonl` 的关键字段

以下字段除前三行外均位于 `target` 对象内：

| 字段 | 含义及单位 |
|---|---|
| `frame_id` / `timestamp_ns` | 本次记录中的帧序号 / 图像时间 ns |
| `tracker_state` | `lost`、`detecting`、`tracking`、`temp_lost` 等外层状态 |
| `estimator_ms` | Tracker 本次处理耗时；不含检测网络、相机、瞄准控制和记录文件序列化，不是整帧延迟 |
| `state[0…10]` | `[cx, cy, cz, vx, vy, vz, a, w, rf, rl, hl]`；m、m/s、rad、rad/s |
| `P` | 对应上述顺序的完整 11×11 当前状态协方差，可检查交叉项和正定性 |
| `report.detections/legal/associated` | EKF 此次收到、合法、关联成功的板数；不等同于原始检测数组总数 |
| `report.ambiguous/quality` | 关联是否有歧义 / 本帧更新质量判定；都不是真值准确率 |
| `report.prediction_rms` | 关联阶段先验投影与观测的角点 RMS，px |
| `report.association_cost/second_cost` | 最佳/次佳关联代价，用来分析歧义，不直接当作像素距离 |
| `report.matches/swapped` | 各模型板的匹配索引及端点交换标志；匹配索引不是原始 `observation_id` |
| `accepted/rejected` | 本帧接受/拒绝的四维端点对更新次数；不是帧数 |
| `accepted_frames` | 当前模型累计成功更新帧数，重建/候选接管时可能发生变化 |
| `residuals[i]` | `valid`、`r=[上u,上v,下u,下v]`、`nis`；r 为观测减预测，单位 px |
| `health/reliable` | 恢复管理器健康状态 / 当前预测是否可靠 |
| `last_accepted_age` | 距恢复管理器最近认可的清晰、合格更新的时间，s；不等于“距任意一次接受更新” |
| `event` | 例如 `candidate_created`、`candidate_takeover`、`main_recovered`、`fit_budget_exceeded` |
| `candidate_active/id`、`recoveries`、`candidate_failures` | 候选状态和当前目标的累计计数；不是全程重建次数 |
| `window_begin/end`、`prior_time`、`candidate_time` | 拟合窗口、先验和候选的时间，steady clock 秒；需要减去统一起点 |
| `validation_frames/rms`、`fit_cost` | 候选后续确认情况、确认投影误差和拟合目标值；不是实际世界误差 |
| `report.association_ms/update_ms` | 关联、更新部分的耗时，不包含整个恢复流程 |

`cz` 是参考板组的高度，另一组高度为 `cz+hl`，不一定等于仿真整车几何中心的 z。`rf`、`rl` 是两组独立半径，第二半径不需要再加 `rf`。

`health` 编码：`0 INIT`、`1 HEALTHY`、`2 COASTING`、`3 DEGRADED`、`4 LOST`。它与外层 `tracker_state` 是两个状态机，不能混为一谈。

`report.reject_reasons` 编码：`0 无效观测`、`1 重复观测`、`2 候选数量限制`、`3 相机模型无效`、`4 无关联`、`5 关联歧义`、`6 投影失败`、`7 新息系统无效`、`8 NIS 门控`、`9 状态越界`、`10 协方差无效`、`11 端点对不支持`。同一帧可有多个原因，其数量不必等于 `rejected`。

### 3.3 当前没有自动保存的数据

- 仿真真值、仿真帧号和稳定目标 ID。不能仅凭现有 JSONL 计算绝对位置/角度真值误差、NEES 或命中率。
- 每次初始化的 `pose_status/pose_rms_px`。当前只在 Foxglove 中文状态表显示；诊断初始化时需要同时保留该状态信息。仅有 `target: null` 不能区分“没有合法板”和“初值验收失败”。
- 每次更新的完整先验、`H/S/K`，以及所有内部失败快照。日志中的后验 `P` 不能直接替代计算该次 NIS 时使用的先验 `P`。
- 原图、连续原始 IMU、下位机反馈时刻。不能从本日志验收检测网络、相机—IMU 延时标定或真实云台闭环延迟。

这些缺项不会阻止残差、稳定性和恢复事件分析。若下一步需要精度验收，应补齐同帧真值及坐标映射后再计算，而不是用状态平滑程度代替精度。

## 4、按顺序进行的仿真场景

先用一辆受支持的四板目标，保持其他设置不变。下面的距离和时间是建议试验条件，不是已完成的测试结果；只使用当前仿真器实际支持的操作，并记录实际值。

| 顺序 | 用户操作 | AI 重点分析 |
|---|---|---|
| 1 初始化 | 静止目标，分别在约 2/4/7 m 和正视/斜视下重新启动跟踪，每类重复至少 3 次 | 从首次合法观测到出现目标、到 `reliable=true` 的时间；失败状态；是否存在固定距离/朝向失败 |
| 2 静态基线 | 目标、底盘、云台均保持静止，采集 20～30 s | 残差偏置、NIS、车心/几何漂移、状态边界、P；不能只看最后一秒 |
| 3 相机运动 | 静止目标、底盘不动，让云台缓慢往返转动，目标保持可见 | 世界系估计是否随云台角度漂移；若有，先查姿态对应、时间和外参 |
| 4 平移 | 目标匀速横移，再反向，记录转向时段 | 机动后的残差持续时间、速度跟随、丢失、P 增长；有同步真值才量化滞后和准确率 |
| 5 小陀螺 | 固定中心，低速/高速匀速旋转，再改变转速或反向 | 换板关联、几何是否漂移、w 是否异常跳变、NIS 尖峰是否持续，以及恢复事件 |
| 6 遮挡与恢复 | 分别遮挡约 0.05/0.10/0.20/0.60 s 后恢复可见，多次重复 | 保留、可靠性下降、候选建立/接管、旧轨迹恢复、完全丢失后的重新初始化 |
| 7 干扰 | 单目标通过后，再增加同类目标、部分遮挡、远距离小板 | 是否错误关联/接管；不能只统计“还有一个目标输出” |

**遮挡测试要保持图像帧持续输入。** 暂停仿真器或阻塞程序会触发另一类问题：Tracker 的 `max_frame_gap_s` 默认 0.1 s，超时会将外层状态设为 `lost`。如需测输入中断，应单独命名并记录实际帧间隔。

当前恢复拟合要求窗口覆盖至少两个模型板编号；长期只看见同一块板时，候选可能无法成立。普通短暂遮挡也不一定需要候选接管，原轨迹恢复是有效路径。

## 5、AI 分析步骤和判断方法

### 5.1 先检查数据，再评价算法

1. 核对源码、配置、检测模型以及入口。两份 JSONL 的帧号/时间应对应；单独列出缺行、非递增时间、超时和尾部不完整记录。
2. 按时间画 `tracker_state`、`health`、`reliable` 和原始检测数，先找出“没有输入”“有检测但初始化失败”“有目标但无有效更新”。外层 `tracking` 不等于本帧估计可靠。
3. 对有目标的记录检查状态/P 是否为有限数、状态是否越界、P 是否近似对称及正定。微小数值误差应结合容差说明；不能用缺失值补零。`target:null` 段的内部数值状态无法由日志证明正常。
4. 用图像时间计算持续时长；帧率变化时同时报告帧占比和有效时间占比，输入中断单列。不要用 Foxglove 的消息接收时间测算法延迟。

### 5.2 残差、NIS、几何联合看

- 按有效端点对分别统计四个有符号残差的均值、RMS、绝对值 P95，以及 NIS 的中位数/P95/阈值超限比例。区分启动、稳定、换板、机动和遮挡恢复阶段；样本数必须一起列出。
- 残差是单条四维更新前、门控前的记录，包含被拒绝的有效尝试。后续端点对使用前一次顺序更新后的状态/P；它们并不共享一份整帧先验。`prediction_rms` 则来自关联阶段，不能混成同一指标。
- 默认 NIS 参考阈值 9.488、拒绝阈值 13.277。门控还受累计更新帧数和模型运行时间预热条件限制；读取本段配置及源码默认值，不能只看 `nis_gate_enabled=true` 就认为从首帧开始拒绝。
- Foxglove 的 `pixel_nis_max` 是一帧多个有效端点对中的最大值。它不服从单条四维 NIS 的同一个分布，不能要求其超线比例恰好为 5%。关联筛选、顺序更新也会影响统计解释。
- `null/valid=false` 表示没有该条有效诊断，不是“残差为零”。接受率可写为 `Σaccepted/Σ(accepted+rejected)`，分母为零时记为不可计算；另报完全无关联/无尝试的帧数，避免掩盖丢失。
- 持续同方向残差优先查几何、时序、角点偏置；机动时残差持续增大再查过程噪声。P 收缩而实际漂移仍大，不能解释为精度提升。
- 半径/高差触边、反复跳变要结合关联编号和重建解释。四板模型相位可相差 90° 并伴随板组交换；跨重建直接比较 `a/rf/rl/hl` 可能把等价编号变化误判为物理跳变，应比较重建出的四块板几何。

### 5.3 恢复、初始化与耗时

每次异常列出“发生帧号/时间 → 当时观测 → 拒绝或失效原因 → 候选/原轨迹变化 → 恢复后的稳定程度”。恢复时间定义为恢复可见后，到再次满足选定的可靠条件的时间，并明确所用条件。

候选恢复统计 `candidate_created`、`candidate_takeover`、`main_recovered`、`candidate_expired_or_identity` 等事件，配合 `validation_rms` 与失败原因。当前目标的累计计数会随重建重置，不可直接用整段最后一个 `recoveries` 充当总次数；日志也未保存全局 `track_id/reinit_count`，同帧重建可能不能被完整识别。

初始化使用统一受约束的像素位姿解算，再由 Target 消费已验收结果。当前入口失败原因需要看状态表。分别记录失败率和成功后稳定性，不能只挑成功片段，也不能因为跟踪阶段 PnP 失败就推断像素 EKF 更新必然失败。

统计 `estimator_ms` 的 P50/P95/P99/最大值，注明机器、帧率和是否连接 Foxglove。`fit_budget_exceeded` 表示候选拟合达到墙钟时间预算，先区分算力不足与数学失败。当前回放也受此预算影响，同一输入在不同机器/负载下未必逐位一致。

### 5.4 有真值之后才能做的精度验收

先验证目标身份、坐标轴/原点、角度零位、图像与真值时间的对应关系，再计算同一目标的 XY 位置误差、角速度误差和预测误差。底盘移动时还要处理移动坐标原点。角度需要处理环绕及四板相位等价；z/半径/高差没有对应真值时不评分。

当前 `center_err` 的发布实现会用第一次估计与第一个候选真值建立 XY 偏移，再寻找最近目标，可能消除初始偏差或匹配错车，**不能直接当作绝对车心精度**。当前真值结构也没有保留稳定目标 ID 和帧号；相机读取“最新真值”不等于已验证同帧。

若补齐同步真值，可报告位置/角速度 RMSE、P95、最大误差和失锁时长。评估 0.05/0.10/0.20 s 预测时，使用当时状态向未来预测，再与未来同一目标真值比较，不使用未来更新后的状态冒充当时预测。没有真值时，这些结果标记为“未验证”。

## 6、用固定输入验证调参

### 6.1 编译与回放

回放只运行记录中的角点、相机姿态、Solver 和 Tracker，不需要再次运行检测器或仿真器。单独的 `build-ekf` 用于避免覆盖正常程序的构建配置：

```bash
cmake -S . -B build-ekf -DEKF_ONLY=ON -DBUILD_TESTING=OFF
cmake --build build-ekf --target ekf_replay -j2
```

把下面的路径替换为终端打印的实际数字目录。输出文件必须尚不存在；重跑时换一个输出名。

```bash
run_dir='/实际路径/logs/ekf_eval/场景_日期时间/数字目录'
HHH_EKF_RECORD_DIR="$PWD/logs/ekf_replay" \
  ./build-ekf/ekf_replay "$run_dir" "$run_dir/replay_baseline.jsonl"
```

回放末尾的 `available` 只表示输出目标非空的帧数，包括保留轨迹的情况，不是准确率。显式输出文件包含帧号、时间、状态和目标诊断，不包含 `estimator_ms`；回放内部 Tracker 还会自动生成一份记录，放在上面指定的 `logs/ekf_replay` 中，勿与在线输入混淆。

先用原配置回放一次，核对在线/回放差异，再改参数。参数对照时复制原记录到一个新目录，至少保留 `config.yaml` 和 `observations.jsonl`；只编辑副本配置，记录修改项及原记录来源。保留原始 manifest，不把其中旧配置摘要误称为修改后的摘要。回放没有 `--config` 参数，读取的是输入目录里的 `config.yaml`。

不得在该输入副本上改变相机内参、畸变或外参来比较同一输入：回放会核对记录中的相机信息，且原始姿态本身已经过当时的外参处理。检测器参数变化必须重新采集。

### 6.2 调参顺序

| 现象 | 先排查 | 确认后可调整 |
|---|---|---|
| 初始化失败集中在斜视/远距离 | 角点顺序、板尺寸/倾角、内外参、状态表失败原因 | `ekf.init_max_rms_px`；放宽会接受更差初值，应同时检查失败率与后续稳定性 |
| 静止时像素误差随机抖动、NIS 持续偏大 | 角点噪声和姿态抖动，是否存在系统偏置 | `ekf.noise_observation` 是方差 px²；例如 100 对应标准差 10 px，不是 100 px |
| 平移机动后估计跟随慢 | 时间对应、关联、检测帧率 | `ekf.q_accel_xy`；z 方向单独看 `q_accel_z` |
| 转速变化后相位/转速跟随慢 | 换板关联、角度环绕和输入时序 | `ekf.q_alpha`；增大通常更灵敏，也会增加噪声响应 |
| 半径/高差长期锁在错误值 | 初始化、几何可观测性、板组对应 | `ekf.noise_radius_forward`、`ekf.noise_radius_lateral`、`ekf.noise_height_lateral`，以及对应初始协方差 |
| 经常 NIS 拒绝 | R/Q 是否合理、投影和关联是否错误、是否已经过预热 | 最后才考虑门控阈值；不能靠持续放宽阈值隐藏偏差 |
| 候选常超时或无法接管 | `event`、窗口内不同板覆盖、确认阶段误差、CPU 耗时 | 对应 `recovery.*` 参数；先定位触发/拟合/确认哪个环节失败 |

一次只改变一个参数或一组同义参数，比较同一输入上的基线和修改结果，并在另一段独立输入上复核。每次结论同时包含精度证据或其缺项、稳定性、恢复和耗时，不能以“更平滑”或“NIS 更低”单独决定保留修改。

### 6.3 当前需要单列验证的问题

- **暂丢可靠性：** `RecoveryManager` 当前要求 `health==HEALTHY` 才能 `reliable=true`，所以 `COASTING` 时即使小于 `coast_s` 也不可靠；不能把 `coast_s=0.15` 解释为必然有 0.15 s 可靠预测。
- **恢复目标函数：** 恢复拟合使用 Huber 权重，但线搜索比较的是随残差重新加权的平方和，不是同一 Huber 损失表达式。异常点场景应检查收敛与接管稳定性，不能仅靠降低 RMS 阈值判定实现正确。
- **关联歧义：** 歧义会被标记、影响质量与恢复；当前并不意味着主滤波器整帧停止更新。检查同类目标干扰时是否仍发生状态偏移。
- **观测不足：** 单板窗口不满足候选多板覆盖要求；无候选不自动等于恢复逻辑失效。
- **数据不足：** 初始化细分原因、全程轨迹编号和同帧真值未进入自动记录。需要这些结论时先补齐证据，不能由空值或最终计数反推。

上述是测试关注点，不代表本次已经修改了实现。

## 7、交给 Linux 侧 AI 的任务

可直接发送以下文字，并给出实际工程路径、仿真器名称和本次记录目录：

> 阅读 `doc/EKF仿真测试指南.md`，以当前 Linux 源码为准核对仿真入口和时间对应。先确认数据可用，再按初始化、静态、云台运动、平移、小陀螺、遮挡恢复的顺序测试。主要分析自动记录的 observations.jsonl 与 trace.jsonl，结合 Foxglove 五个曲线、3D 和状态表核对异常。每个结论给出记录目录、frame_id/时间段和实际字段数值；没有真值的指标写未验证。先报告问题和单项调参建议，保留原记录及配置，用 ekf_replay 验证同一输入；不要把接入失败、预期遮挡或图表空值说成 EKF 发散。

AI 每轮反馈只需包含：

1. 本轮场景、版本/配置、数据是否完整。
2. 核心结果：初始化时间、有效/可靠时长、残差/NIS、几何与 P、恢复事件、耗时；不可获得的项目明确注明。
3. 最多三个主要问题，每个附具体帧号和证据。
4. 下一步仅建议一个明确修改及预期影响；如已获准验证，列出同输入对照结果。
